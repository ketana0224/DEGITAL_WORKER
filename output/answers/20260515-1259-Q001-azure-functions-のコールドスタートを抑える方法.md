# Q001: Azure Functions のコールドスタートを抑える方法

## TL;DR

- Premium プランまたは Flex Consumption プランの **Always Ready Instance** を利用することで、事前にウォームアップされたインスタンスを確保し、コールドスタートを抑制できます [1][2]
- 従量課金 (Consumption) プランではコールドスタートを完全に排除できませんが、**依存関係の最適化**や**ウォームアップトリガー**の活用により影響を軽減できます [3]
- .NET の場合は **ReadyToRun (R2R) コンパイル** の利用も有効です [4]

## ✅ 事実 (公式ドキュメント・一次情報に記載あり)

### 1. ホスティングプランの選択

Azure Functions のコールドスタート特性はホスティングプランによって大きく異なります。

| プラン | コールドスタート | Always Ready | 備考 |
|--------|------------------|--------------|------|
| Consumption (従量課金) | あり | ❌ 不可 | 最もコールドスタートの影響を受けます [1] |
| Flex Consumption | あり（軽減可） | ✅ 可 | Always Ready インスタンスを設定できます [2] |
| Premium (Elastic Premium) | 軽減可 | ✅ 可 | 最低 1 インスタンスが常時ウォームです [1] |
| Dedicated (App Service) | なし | — | 常時稼働のため該当しません [1] |
| Container Apps | あり（軽減可） | ✅ 可 | 最小レプリカ数を 1 以上に設定できます [1] |

### 2. Premium プランの Always Ready Instance

Premium プラン (Elastic Premium) では、**常時使用可能なインスタンス (Always Ready Instance)** を設定できます。これにより、指定した数のインスタンスが常にウォーム状態で維持されます [1]。

### 3. Flex Consumption プランの Always Ready

Flex Consumption プランでも、関数グループごとに Always Ready インスタンス数を指定できます。HTTP トリガーや Durable Functions トリガーなどの関数グループに対して、常にウォーム状態のインスタンスを確保できます [2]。

### 4. ウォームアップトリガー (Warmup Trigger)

Azure Functions は `warmup` トリガーを提供しています。新しいインスタンスがスケールアウトで追加される際に、このトリガーが先行して実行され、依存関係の初期化やキャッシュの準備を行えます [3]。

```csharp
// C# でのウォームアップトリガーの例
[Function("Warmup")]
public void Run([WarmupTrigger] object warmupContext, FunctionContext context)
{
    context.GetLogger("Warmup").LogInformation("Function App instance is warm.");
    // 依存関係の事前初期化などをここで行います
}
```

### 5. 依存関係と起動時間の最適化

コールドスタート時間を短縮するために、以下の対策が公式ドキュメントで推奨されています [4]。

- **不要な依存関係を削除する**: パッケージサイズを最小化し、読み込み時間を短縮します
- **遅延読み込み (Lazy Loading) を活用する**: 必要になるまでモジュールの読み込みを遅延させます
- **.NET の場合は ReadyToRun (R2R) コンパイルを使用する**: JIT コンパイルを事前に行い、起動時間を短縮します
- **接続のプーリングを使用する**: HTTP クライアントや DB 接続を `static` で再利用します

### 6. 言語ランタイム別の考慮事項

コールドスタート時間は言語ランタイムによっても異なります。一般的に、コンパイル言語 (C#) はインタープリター言語 (Python, JavaScript) よりもコールドスタートが短い傾向にあります [4]。
